## 問題の形

- 本番に近いシナリオ問題にする。状況を書き、要件(最小のコスト、最小の運用負荷など)を最後の一文で問う。
- 単一選択(4択)を7割、複数選択(5択から2つ)を3割。複数選択は問題文の最後に「（2 つ選択）」と書く。<試験ガイドに並べ替え、内容一致、ケーススタディがあれば、その割合を書く。無ければこの行の後ろの3つを消す>
- 並べ替え(`order`)は、作業の手順や処理の流れのように、順序に一つの正解がある題材だけで作る。人によって順序が入れ替わりうるものは使わない。
- 内容一致(`match`)は、プロンプトごとに合う答えが一つに決まるようにする。
- ケーススタディは、1つのシナリオに2〜4問の設問を付ける。各設問は個別に採点されるので、設問どうしで答えが依存しないようにする。
- 不正解の選択肢も「ありそう」に作る。明らかに的外れな選択肢は入れない。
- 正解の位置を偏らせない。単一選択なら A/B/C/D がほぼ均等になるよう散らす。
- 市販の問題集や本番の問題を写さない。オリジナルで作る。

## 解説の書き方

- explanation は 200〜450 字程度。なぜその答えになるか、決め手になった要件の語句と、正解の仕組みを書く。
- optionNotes は選択肢ごとに 1〜2 文。正解はなぜ要件を満たすか、不正解はどこが要件に合わないか。
- refs に裏取りに使った公式ページの URL を1〜3件付ける。実在を確かめた URL だけを書く。
- <文体の決まりがあれば書く。例: です・ます調で統一する、太字を使わない>

## 出力の形式

JSON 配列 1 ファイル。各要素は次の形。

```json
{
  "id": "D1-001",
  "domain": 1,
  "task": "1.1",
  "type": "single",
  "question": "ある企業は……。これらの要件を満たすものはどれですか。",
  "options": ["選択肢A", "選択肢B", "選択肢C", "選択肢D"],
  "answer": [2],
  "explanation": "……",
  "optionNotes": ["Aの解説", "Bの解説", "Cの解説", "Dの解説"],
  "services": ["関係する製品や制度の名前"],
  "difficulty": 2,
  "refs": [{ "title": "ページのタイトル", "url": "https://..." }]
}
```

- `type` は `single` `multi` `order` `match` のどれか。`single` のとき options は 4 個、answer は 1 個。`multi` のとき options は 5 個、answer は 2 個以上で、問題文の最後に「（N つ選択）」と書く。
- `answer` は 0 始まりの添字の配列。
- `domain` と `task` は [`exam.json`](exam.json) の分野と細目の番号に合わせる。`domain` は数値(`1`)、`task` は文字列(`"1.1"`)で書く。`domain` を `"1"` と書くとビルドが止まる。
- `difficulty` は 1(基本)〜3(難しい)。2 を中心に。
- `services` と `refs` は無くてもよい。あれば解説の下に出る。
- 書き終えたら `python3 -c "import json;d=json.load(open('<path>'));print(len(d))"` で読めることと件数を確かめる。


並べ替えは `type` を `order` にする。`options` は並べる候補で3〜6個、`answer` は正しい順に並べた候補の添字で3〜5個(重複なし)。`answer` が `options` より短ければ、候補の一部だけを使う問題になる。問題文には「次の候補から 3 つを選び、正しい順序に並べてください。」のように、使う数を書く。`optionNotes` は候補ごとに、何番目に来るか、または使わない理由を書く。

```json
{
  "id": "D1-002",
  "domain": 1,
  "task": "1.2",
  "type": "order",
  "question": "ある企業は……を行いたいと考えています。次の候補から 3 つを選び、正しい順序に並べてください。",
  "options": ["手順A", "手順B", "手順C", "手順D"],
  "answer": [2, 0, 3],
  "explanation": "……",
  "optionNotes": ["2番目に来る理由", "使わない理由", "最初に来る理由", "最後に来る理由"],
  "difficulty": 2,
  "refs": []
}
```

内容一致は `type` を `match` にする。`prompts` はプロンプトで3〜7個、`options` は答えの候補で2〜7個。`answer[i]` はプロンプト i に合う `options` の添字で、`prompts` と同じ数にする。同じ答えを何度使ってもよく、使わない答えがあってもよい。そうした問題では、問題文にその旨を書く。`optionNotes` は答えの候補ごとに、どのプロンプトに合うか、またはどれにも合わない理由を書く。

```json
{
  "id": "D2-002",
  "domain": 2,
  "task": "2.1",
  "type": "match",
  "question": "次の各要件に最も合うものを選んでください。同じものを複数回選ぶことも、選ばないものがあることもあります。",
  "prompts": ["要件1", "要件2", "要件3"],
  "options": ["答えA", "答えB", "答えC"],
  "answer": [1, 0, 1],
  "explanation": "……",
  "optionNotes": ["Aが合う要件", "Bが合う要件", "Cがどれにも合わない理由"],
  "difficulty": 2,
  "refs": []
}
```

ケーススタディは新しい `type` を作らず、どの形式の問題にも `"case": "C1"` のようにシナリオの ID を付ける。シナリオの本文は試験のフォルダの [`cases.json`](cases.json) に、`{"C1": {"title": "題", "scenario": "本文"}}` の形で書く。ページでは設問の上にシナリオが出る。同じ ID の設問は2問以上にし、ID は試験の中で重ならないようにする。分野をまたいで設問を付けてもよい。問題文はシナリオを読んだ前提で書き、シナリオの内容を繰り返さない。

## 完了報告

次の形式で返す。

- ステータス: 完了 / 一部未完了
- 出力ファイル: パスと件数
- タスク別の件数、単一/複数の件数、正解位置の分布
- 検証: 公式の資料で確かめた主な事実と、確かめきれなかったもの
- 懸念と未完了
